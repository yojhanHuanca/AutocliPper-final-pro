# Importación de enlaces: factibilidad y contrato

Fecha de revisión: 2 de noviembre de 2026. Este documento distingue reconocimiento de URL, vista previa oficial y obtención de bytes. Que un enlace se reconozca o se reproduzca en un embed no implica que pueda importarse al almacenamiento de AutocliPper.

### Referencia de la app Java anterior

La app Spring anterior aceptaba enlaces genéricos y usaba `yt-dlp` para obtener metadata (`VideoController.runYtDlpPreview`) y para descargar archivos durante el procesamiento (`VideoProcessingService`). Su implementación intentaba distintos clientes/formatos y podía leer un archivo de cookies o cookies del navegador cuando YouTube bloqueaba la solicitud. Es una referencia de la experiencia que existía, no una API oficial ni una autorización para reutilizar el flujo: no se copió código Java, no se inspeccionaron archivos de secretos/cookies y no se portaron esos mecanismos al backend nuevo. El flujo vigente usa endpoints documentados; mantiene YouTube en metadata/preview únicamente y limita Twitch a su endpoint documentado de descarga de clips.

### Decisión de implementación

La única consulta de enlace habilitada sin OAuth de usuario es metadata pública de YouTube mediante `videos.list`, si la API key del servidor está configurada. Esa integración ya existe y es únicamente preview: no produce un upload, clip ni pipeline. El importador oficial de Twitch ya está escrito, pero la app OAuth no está configurada en el entorno y no hay cuenta con consentimiento comprobado; no se amplió ni se habilitó una importación no verificable. Kick queda en descarga manual desde su interfaz oficial y carga local. No se hicieron llamadas reales a proveedores ni se leyó ninguna credencial para esta revisión.

Consulta oficial revalidada el 31 de octubre de 2026. La cuota predeterminada de YouTube Data API es de 10,000 unidades/día para el resto de métodos, con buckets diarios separados de 100 llamadas para `search.list` y 100 para `videos.insert`; la cuota se renueva a medianoche del Pacífico. Este producto no consulta la YouTube Data API para importar enlaces y esa cuota no habilita descarga audiovisual. El catálogo público actual de Kick Dev enumera OAuth, canales, usuarios, livestreams y otras API, pero no documenta una API para obtener bytes de clips/VOD; por eso no se atribuye una cuota de descarga a Kick. Twitch publica 100 solicitudes/minuto específicamente para `Get Clips Download`; es una cuota del proveedor, separada del límite local conservador de Identity.

## Contrato actual para el cliente

La pantalla actual reconoce formato localmente y muestra embeds del proveedor. La validación remota y la importación deben ser acciones separadas: validar un enlace comprueba proveedor/ID/metadata y permiso actual, mientras importar exige una nueva solicitud autorizada del usuario y una clave de idempotencia. No persistir la URL pegada ni tratar el preview como autorización o promesa de importación.

`POST /v1/projects/{id}/source-links/resolve` devuelve `state`, `importable`, `reasonCode`, `nextAction`, `message` y `nextStep`, además de metadata mínima cuando está disponible; nunca devuelve URLs firmadas de Twitch. YouTube devuelve `unsupported/YOUTUBE_DOWNLOAD_APPROVAL_REQUIRED`, `videoId` y el `previewUrl` oficial de IFrame, con acción `upload_authorized_file`; la URL de preview sirve solo para que el cliente muestre el reproductor oficial y no autoriza ni habilita la importación. Kick devuelve `unsupported/KICK_MEDIA_API_UNAVAILABLE` con la misma acción y explica que se debe descargar desde Kick y cargar el MP4. Twitch sin app configurada devuelve `unavailable/TWITCH_OAUTH_NOT_CONFIGURED`; sin cuenta vinculada, `unavailable/TWITCH_ACCOUNT_NOT_LINKED`; ambos estados indican el siguiente paso. Una respuesta Twitch disponible solo informa que Helix entregó una URL de descarga para la cuenta vinculada y ese clip; no garantiza que la transferencia, la inspección ni el pipeline vayan a completarse. `POST /v1/projects/{id}/source-links/import` devuelve `succeeded` con `uploadId` e inspección `queued`, o `importing` para una solicitud idempotente que sigue en curso. Sus errores conservan códigos seguros y acción: YouTube/Kick HTTP 422, Twitch OAuth sin configurar 503, cuenta sin vincular 409, rol insuficiente 403 y limitación 429. El frontend puede traducir `nextAction`; no debe tratar `unsupported`, `unavailable` ni una vista previa como fuente procesable. El importador no crea el pipeline automáticamente: el cliente consulta `GET /uploads/{uploadId}` y solo después de `inspection.status=succeeded` y audio compatible inicia `POST /uploads/{uploadId}/pipelines`, cuyo preflight aplica selector, presupuesto y cuota. No se devuelve el enlace temporal al navegador ni se crea una carga cuando la importación falla.

La última lectura local de providers, del 1 de noviembre, reportó `twitch.configured=true`; no confirmó OAuth real, cuenta vinculada ni permisos de canal. No se aceptan tokens Twitch aportados por el browser ni se trata el login Google como autorización Twitch. Los secretos solo se configuran en el entorno privado de Identity.

## Controles implementados para la importación Twitch

- Analizar solo URLs HTTPS de hosts/rutas conocidos; Twitch y Kick rechazan query/hash. YouTube acepta únicamente el ID en `youtu.be/{id}`, `watch?v={id}`, `/shorts/{id}`, `/embed/{id}` o `/live/{id}`. En YouTube se toleran parámetros conocidos de compartir/tiempo (`si`, `t`, `start`, `end`, `feature`, `list`, `index`, `pp`, `ab_channel`); se descartan tras extraer el ID y nunca se usan para formar peticiones. Se rechazan claves repetidas, redirecciones y parámetros desconocidos. Rechazar userinfo, puertos alternos, credenciales e IDs inválidos. La vista previa YouTube se forma localmente a partir del ID y apunta al host oficial del IFrame; no hace una petición server-side. Helix resuelve el broadcaster Twitch.
- Exigir autorización de proyecto/workspace editor, vinculación OAuth con scope, y comprobación del permiso del usuario vinculado contra broadcaster/editor en `Get Clips Download`. `source_imports` liga las claves idempotentes al proyecto/clip; no guarda URL de usuario ni URL firmada.
- Pedir la URL temporal justo antes de la transferencia. Aceptar solo `production.assets.clips.twitchcdn.net`, resolver DNS con máximo de espera local de 5 s y fijar una respuesta pública, desactivar redirects, limitar la concurrencia local a dos y aplicar límites de tiempo, tamaño, MIME y firma MP4. Si vence el límite DNS, se falla antes de abrir el socket HTTP; la consulta subyacente del resolver del sistema no es cancelable y puede terminar en segundo plano.
- Rechazar metadata Twitch fuera de `(0, 60]` segundos, conforme al máximo de la documentación oficial de clips. El procesamiento local admite videos más largos; 60 s no cambia los límites del upload general. La descarga limita el archivo a 100 MiB, 90 s total y 10 s de inactividad; admite dos transferencias Twitch concurrentes por proceso. Estos son límites locales, no límites del proveedor.
- Calcular SHA-256 al transmitir a temporal privado, cargar al objeto servidor reservado por Project, confirmar el upload y encolar la inspección existente. DNS se resuelve completo, rechaza cualquier respuesta no pública y fija una IP; el GET no sigue redirecciones. Identity cuenta globalmente en Redis y limita a 10 operaciones por ventana fija de minuto; el diseño cubre el doble de operaciones por rollover más una repetición de `/clips/downloads` al renovar token (40 llamadas conservadoras por minuto, frente a 100 oficiales). Project consulta `used_bytes + reserved_bytes` antes de contactar Identity y limita la transferencia al espacio libre observado, hasta 100 MiB; si no queda espacio, falla antes de pedir una URL temporal. La intención de upload vuelve a reservar los bytes exactos dentro de una transacción, que sigue siendo el control autoritativo frente a imports concurrentes. El pipeline aplica sus propias reservas y concurrencia. El cleanup borra temporales y un upload no confirmado sigue sujeto al cleanup de uploads existente.
- La clave idempotente y la unicidad proyecto/clip se reclaman antes de las llamadas externas. Si un intento previo dejó un upload pendiente y su lease venció, el retry reutiliza el mismo objeto reservado, vuelve a descargar el mismo clip y exige coincidencia de bytes y SHA-256 antes de sobrescribirlo. Si el upload ya está confirmado, el retry reconcilia `source_imports` con ese upload e inspección sin descargar de nuevo. La transición a confirmado, el enqueue de inspección y el estado `succeeded` de la importación se escriben en la misma transacción. Un upload pendiente expirado o abortado espera el cleanup existente antes de crear otro intento; si su contenido cambia, se devuelve `TWITCH_SOURCE_CHANGED` y se limpia el upload pendiente. La falta de cuota se expresa como `PROJECT_STORAGE_QUOTA_EXCEEDED` (409), los clips por encima del tope local como `TWITCH_DOWNLOAD_TOO_LARGE` (413), y los fallos transitorios permanecen retryables sin exponer URLs firmadas ni mensajes del proveedor.
- No cachear metadata de YouTube fuera de sus políticas; no importar directos en curso de ningún proveedor. Los jobs y artefactos deben respetar la autorización de autor y el workspace durante cada transición.

## Cobertura y prerequisitos externos

El flujo OAuth usa Authorization Code server-side y solicita solo `editor:manage:clips` y `channel:manage:clips`, necesarios según la persona vinculada actúe como editor o broadcaster. `POST /v1/auth/twitch/link` requiere sesión y CSRF, crea `state` aleatorio de un uso con expiración de cinco minutos y lo liga a una cookie de callback; `GET /v1/auth/twitch/callback` intercambia el código, valida client ID, que se haya concedido al menos uno de esos scopes y user ID; `DELETE /v1/auth/twitch/link` revoca en Twitch best-effort y elimina la conexión local. `GET /v1/auth/twitch/link` expone solo estado y nombre de cuenta. Access y refresh tokens se cifran con AES-GCM usando `AUTH_ENCRYPTION_KEY` y contexto por usuario. El servicio valida el token al iniciar, cada hora y antes de usar la conexión, y persiste el refresh token rotado.

El cliente usa `POST /v1/projects/{id}/source-links/resolve` para comprobar metadata y permiso actual y `POST /v1/projects/{id}/source-links/import` con `Idempotency-Key` para importar. La URL pegada no se persiste y una URL firmada no llega al browser. La transferencia acepta únicamente HTTPS al hostname `production.assets.clips.twitchcdn.net` observado en el ejemplo oficial, fija una dirección DNS pública por conexión, rechaza respuestas privadas/reservadas y redirects, limita DNS a 5 s y valida MIME/firma MP4, tamaño máximo 100 MiB, 10 s de inactividad y 90 s total; limpia el temporal local. Tras calcular SHA-256, crea una intención de upload del proyecto, sube el archivo al bucket existente y confirma el upload para encolar la inspección actual. `source_imports` deduplica por clave de idempotencia y proyecto/clip; no guarda URL temporal ni secreto. El importador no inicia el pipeline: el cliente debe esperar inspección exitosa y luego la creación estándar aplica preflight, presupuesto, cuota y contrato.

Para habilitarlo, registra una app Twitch con 2FA en la cuenta dueña. Configura `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET` y `TWITCH_REDIRECT_URI` solo en el entorno privado de Identity; el redirect exacto de este entorno es `http://localhost:3005/v1/auth/twitch/callback`. El callback exitoso regresa a `/settings?provider=twitch&status=linked` en `CORS_ORIGIN`. El secreto no se guarda en el repo. `GET /v1/auth/providers` y `GET /v1/auth/twitch/link` reportan `configured:false` hasta que los valores sean válidos. La persona debe vincular Twitch y conceder el scope. Las migraciones locales de Identity y Project ya están aplicadas y verificadas; la prueba externa real todavía requiere la app, consentimiento y un canal donde el usuario conectado tenga rol de broadcaster/editor.

Comprobación local del runtime el 20 de octubre de 2026, sin reiniciar servicios: Gateway, Identity, Project, Analysis y Renderer estaban saludables. `GET /v1/auth/providers` en Gateway (`localhost:3005`) responde 200 con `twitch.configured:false`; `GET /v1/auth/twitch/link` sin sesión responde 401. Un `POST /v1/projects/{id}/source-links/resolve` sin CSRF responde 403 en la barrera CSRF; eso confirma que la ruta está publicada, pero no prueba el resultado autenticado de resolución. No se probaron autorización OAuth, importación autenticada ni descarga real. La app Twitch aún no está registrada/configurada. Las migraciones `0013_twitch_oauth_links` y `0012_twitch_source_imports` ya se aplicaron a las bases locales y se verificaron, pero la integración no se puede habilitar hasta configurar la app y vincular una cuenta. `tests/acceptance/twitch-http.test.mjs` requiere un backend desechable y Mailpit; su `API_BASE_URL` por defecto es `127.0.0.1:3000` y la ejecución aquí respondió 500 antes de crear una cuenta. El único origen que puede entrar al procesamiento local hoy es un archivo de video cargado e inspeccionado. El pipeline automático sigue bloqueado por el selector. Ninguna URL de YouTube, Kick o Twitch es importable en el runtime actual; Twitch queda como capacidad de código pendiente de credenciales/consentimiento y despliegue local.

## Descarga oficial de Kick (consulta 31 de octubre de 2026)

La [ayuda oficial de clips de Kick](https://help.kick.com/en/articles/7120566-how-to-create-clips-on-kick) documenta un botón **Download** que guarda el clip visible como MP4. Alternativa admitida: que la persona descargue el clip desde la interfaz oficial al que tenga acceso y lo suba como archivo local. La [ayuda de VOD](https://help.kick.com/en/articles/7832538-how-to-download-your-kick-vod) actualmente describe herramientas de terceros y copiar manualmente una playlist m3u8; eso no constituye un endpoint de la API oficial ni una autorización para que este producto automatice esa obtención, así que el backend no lo implementa. Para VOD, usar un archivo original o una opción oficial de descarga que Kick proporcione directamente a esa cuenta. No usar extractores de streams, playlists HLS ni servicios de terceros como parte del producto. Ninguna ruta oficial documentada ofrece a esta app un endpoint autenticado para importar bytes desde una URL, por lo que Kick sigue rechazado por servidor.

## API de Twitch y corte backend (consulta 31 de octubre de 2026)

La revisión actual de Helix confirma que `Get Clips Download` continúa marcado `NEW`; entrega URLs temporales con expectativa de expiración. Su límite publicado es 100 solicitudes/minuto, permite hasta 10 `clip_id` por llamada y requiere `editor:manage:clips` o `channel:manage:clips`. El `editor_id` debe coincidir con el usuario del token; Twitch indica 403 cuando no tiene rol de editor para el broadcaster. Esto no extiende la autorización a VOD completos ni a directos. Véanse [referencia Helix](https://dev.twitch.tv/docs/api/reference/#get-clips-download), [OAuth Authorization Code](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [validación obligatoria de tokens](https://dev.twitch.tv/docs/authentication/validate-tokens/) y [registro de apps](https://dev.twitch.tv/docs/authentication/register-app/). El registro requiere cuenta Twitch con 2FA, redirect URL y, para Authorization Code, client secret confidencial.

`resolveSourceLink` es un parser puro: reconoce hosts/rutas HTTPS exactos, rechaza credenciales, puertos alternos, fragmentos e IDs que no sean slug. Rechaza query strings para Twitch y Kick; para YouTube admite solo los parámetros de compartir/tiempo permitidos arriba y usa únicamente el ID extraído. `Get Clips` oficial resuelve el slug y entrega broadcaster, título y duración; `Get Clips Download` comprueba el broadcaster/editor con el token Twitch vinculado. El `editor_id` siempre sale del token validado, nunca del browser. YouTube permanece `unsupported/YOUTUBE_DOWNLOAD_APPROVAL_REQUIRED` y Kick `unsupported/KICK_MEDIA_API_UNAVAILABLE`.

La lista [oficial de Kick Dev](https://docs.kick.com/llms.txt) enumera OAuth, canales, usuarios, livestreams, chat y moderación, pero no documenta un API de clips ni descarga de archivos. La ayuda de Kick sí recomienda herramientas de terceros para descargar los VOD propios y el botón **Download** de su interfaz para bajar clips como MP4. Sin embargo, los [Términos de Kick](https://kick.com/terms-of-service) prohíben sistemas automatizados para acceder al servicio y acceder a contenido por tecnología no proporcionada o autorizada; los [términos de Kick Dev](https://dev.kick.com/terms-of-service) exigen que una integración no facilite usos que violen esos términos. La guía de descarga no documenta una API para que AutoClipper resuelva y transfiera esas URL, ni autoriza explícitamente una descarga server-side automatizada. Por esa tensión, se infiere que los ejemplos oficiales respaldan el uso de las herramientas indicadas por la persona para su VOD, pero no bastan para habilitar un extractor automatizado de AutoClipper. Kick permanece `unsupported/KICK_MEDIA_API_UNAVAILABLE` hasta que Kick publique un endpoint aplicable o dé permiso programático por escrito. La respuesta del backend explica este límite y permite cargar un MP4 obtenido por la ruta oficial/manual.

La cobertura automatizada comprueba el parseo estricto, IPs IPv4/IPv6 especiales, DNS fijado y timeout DNS, redirects, MIME/tamaño/firma, scopes, autorización, almacenamiento privado, confirmación de inspección y deduplicación. Los tests usan bytes/CDN/credenciales de fixture: uno recorre el VOD con intervalo, creación simulada del clip, persistencia del ID, descarga simulada, upload privado y cola de inspección; otro recorre el clip hasta inspección simulada y `PipelineManager.begin` con el contrato manual Whisper-only (`selection.mode=none`), y comprueba que el pipeline responde conflicto antes de que la inspección termine. No simulan OAuth/CDN reales, selección automática ni llamadas pagadas a OpenAI/Gemini u Ollama. Verifican el `uploadId`, retry con la misma clave y deduplicación. La reserva de almacenamiento se delega a la intención de upload estándar, que aplica la cuota del workspace antes de subir los bytes; la creación del pipeline mantiene sus propias reservas. No existe aceptación end-to-end con una cuenta Twitch enlazada, medio real, inspección real ni render final; el runtime tiene OAuth configurado, pero al 2 de noviembre de 2026 la tabla de vínculos no contiene cuentas enlazadas. La capacidad se mantiene pendiente de una autorización de usuario y de la aceptación real en un entorno autorizado.

Revisión de validación, 2 de noviembre de 2026: un VOD Twitch canónico se resuelve como VOD y pide un intervalo explícito; sin ese intervalo no crea importación. `vodOffsetSeconds` indica el final del clip y se limita por la duración real del VOD; el límite local de 24 horas se retiró porque Helix no publica ese tope. La duración del clip sí se restringe a 5–60 segundos. El contrato Helix describe estos límites y permite el clip VOD bajo los scopes indicados ([Create Clip From VOD](https://dev.twitch.tv/docs/api/reference/#create-clip-from-vod)). La ruta disponible para esos archivos es el upload local autorizado (`POST /projects/{id}/uploads` → PUT firmado → confirmación → inspección → pipeline). Sus controles están cubiertos por tests locales/acceptance, pero la aceptación con storage, PostgreSQL y workers no se ejecutó en esta revisión porque Docker está fuera de servicio. ## Contrato del pipeline comunicado al frontend

`POST /v1/uploads/{uploadId}/pipelines` acepta `version: 2` para generación automática: `clipCount` entero 1–3, `maxDurationSeconds` opcional de 1–120 (omitido = 120), `contentType` cerrado, `aspect` (`source|vertical|square|horizontal`) y `subtitles` (`transcript|none`). El selector OpenAI está predeterminado y exige `OPENAI_API_KEY`, permiso pagado explícito y presupuesto positivo; permanece cerrado por defecto. Gemini es opcional explícito. Ollama devuelve `SELECTION_PROVIDER_NOT_SUPPORTED` y no se usa como fallback. El selector valida cantidad exacta, tiempos, no solapamiento y duración máxima. La salida de video actualmente es siempre MP4/H.264 (AAC cuando hay audio) y el aspecto elige dimensiones/padding; no existe parámetro para elegir contenedor o codec. Con subtítulos transcript se ofrecen video, SRT y VTT; con `none`, solo video. El frontend ya envía estos campos y ofrece la elección de cantidad, duración, tipo, aspecto y subtítulos; debe presentar el formato como fijo hasta que exista una opción real en contrato y renderer.

El flujo de Twitch entrega un `uploadId` con la inspección en cola; el cliente espera inspección exitosa, permite configurar el pipeline en el mismo flujo del archivo y solo entonces lo inicia. El pipeline automático requiere Whisper y el selector seleccionado listos; con OpenAI el presupuesto sigue cerrado por defecto y el preflight responde 503 antes de encolar si falta clave/aprobación/límite. El modo manual por intervalos genera un MP4 sin subtítulos sin depender del selector.

## Actualización de backend (2 de noviembre de 2026)

El parser también admite la URL canónica `https://www.twitch.tv/videos/{id}`. `resolve` responde `input_required/TWITCH_VOD_INTERVAL_REQUIRED` hasta recibir `vodOffsetSeconds` y `durationSeconds`; el contrato local exige segundos enteros, duración de 5–60 s y offset al menos igual a la duración. La importación consulta metadata oficial, solicita el clip con `POST /helix/videos/clips`, guarda primero el ID remoto y luego usa el flujo existente de descarga de clip, reserva, inspección y upload privado. No descarga el VOD completo.

La creación de clips es un efecto externo: la marca de inicio se guarda antes del POST; el ID generado se persiste antes de pedir bytes. Si se pierde la respuesta antes de conocer el ID, el import queda `TWITCH_VOD_CLIP_OUTCOME_UNKNOWN` y no repite automáticamente el POST. Si el clip existe pero aún no está descargable, el retry reutiliza ese ID. Lo mismo ocurre si otra carga consume la cuota después del snapshot previo y falla la reserva atómica final: no se confirma ni se guarda un upload fuera de cuota, el `source_imports` fallido conserva `provider_resource_id` y un retry reutiliza el clip en vez de crear uno nuevo. Esto conserva trazabilidad y evita efectos remotos repetidos, aunque el primer clip puede quedar creado en Twitch hasta que haya cuota para descargarlo. La prueba de este caso usa transporte/persistencia simulados, sin OAuth/CDN real. La referencia oficial define `vod_offset` como el final del clip y exige `editor_id` del usuario token; el backend verifica el rol por Helix. [Create Clip From VOD](https://dev.twitch.tv/docs/api/reference/#create-clip-from-vod), [Get Clips Download](https://dev.twitch.tv/docs/api/reference/#get-clips-download).

## Metadatos de YouTube y evaluación de yt-dlp (31 de octubre de 2026)

El resolver autenticado de Project consulta ahora `videos.list` solo después de validar la URL y extraer el ID canónico. La política prohíbe descargar, importar, respaldar, cachear o guardar copias audiovisuales sin aprobación previa escrita de YouTube. La documentación oficial de [yt-dlp](https://github.com/yt-dlp/yt-dlp) lo describe como descargador de línea de comandos con soporte para miles de sitios. Eso describe capacidad técnica del proyecto, no autorización del proveedor, del titular ni del usuario que pegó el enlace. No se incorporó ni ejecutó yt-dlp. Si una ruta futura cuenta con permiso contractual escrito y revisión por proveedor, el diseño recomendado es un worker aislado y versionado que recibe una solicitud firmada de Project después de comprobar el rol editor y el proyecto/workspace; acepta únicamente perfiles explícitos de proveedor y hosts aprobados, no URLs arbitrarias; restringe DNS/egress y redirects a hosts públicos permitidos; aplica límites de tiempo, bytes, duración, CPU, disco y concurrencia; usa clave idempotente y deduplicación por proyecto/ID/hash; escribe en staging privado y solo enlaza el medio al proyecto tras revalidar propiedad, cuota, permisos e inspección. Los errores del extractor se traducen a códigos allowlist sin comandos, URLs firmadas ni mensajes upstream. Debe probarse el ciclo real con cuenta y contenido autorizados antes de declarar soporte. Una aprobación que no cubra la ruta de producto mantiene YouTube en preview/metadatos únicamente.

## Flujo automático solicitado para enlaces (2 de noviembre de 2026)

El requisito actualizado es: pegar URL, elegir cantidad y duración máxima de clips y confirmar una generación automática, sin pedir un segundo final ni segmentos manuales. El pipeline backend v2 ya admite de 1 a 3 clips y un máximo de 1–120 s por clip sobre un `uploadId` confirmado e inspeccionado. Su selector `local` es determinista y sin coste externo; `selectionMode=llm` usa la configuración OpenAI principal o Gemini opcional, pero solo tras autorización de gasto y un presupuesto válido. El pipeline ejecuta Whisper local y FFmpeg; este contrato no afirma relevancia viral cuando se usa el selector local.

La web Spring documentada hacía URL→`yt-dlp`→transcripción/selección→FFmpeg y contemplaba cookies de navegador. Ese extractor genérico y las cookies no se portan: no validan una API de medios autorizada y amplían SSRF/uso de sesiones. La implementación segura disponible por URL es más acotada:

- Un **clip Twitch ya publicado** puede pasar por Helix `Get Clips Download`, OAuth y permiso de canal, convertirse en upload privado e inspeccionarse; después se puede iniciar el pipeline automático existente. El recorrido real Twitch→inspección→pipeline aún no tiene aceptación E2E con proveedor real.
- Un **VOD Twitch** no entrega sus bytes por el endpoint de metadatos. `Create Clip From VOD` exige `vod_offset` y duración de 5–60 s, y crea un clip externo en ese intervalo; no selecciona momentos por sí solo. Como el flujo solicitado no pide segundos manuales, la guía de `TWITCH_VOD_INTERVAL_REQUIRED` ahora dirige a un clip publicado o a subir el MP4 autorizado. La API de intervalo se conserva para clientes explícitos anteriores, pero no demuestra selección automática de un VOD completo. [Referencia Twitch](https://dev.twitch.tv/docs/api/reference).
- **YouTube** se mantiene en preview/metadatos hasta contar con aprobación previa escrita para importar audiovisual. [Políticas YouTube](https://developers.google.com/youtube/terms/developer-policies).
- **Kick** sigue sin endpoint oficial documentado de transferencia audiovisual apto para esta importación; no se implementa scraping, HLS ni `yt-dlp`. Se debe subir un MP4 que la persona haya descargado y esté autorizada a usar. [Índice oficial de Kick Dev](https://docs.kick.com/llms.txt), [términos de Kick](https://kick.com/terms-of-service).

El backend recibe ahora una guía que no pide segmentación manual para VOD Twitch; los archivos propios y clips Twitch publicados pueden avanzar por importación/inspección y el pipeline existente, sujeto a una prueba E2E real antes de anunciar soporte.
